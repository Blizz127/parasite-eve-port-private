# Batch O: retail $v0 of func_80062A7C, returned through func_80044E14

port3 switch-over batch O. The lead approved option (a): a line-by-line
$v0-returning variant, with a differential test.

## Why a hand port

- `src/func_80044E14.c` returns `r = func_80062A7C(D_8009CFA0[idx])`, or 0
  when the table entry is empty.
- `src/func_80062A7C.c` is `void`, but retail leaves a defined `$v0` at its
  single exit.
- The generator still cannot emit `src/func_80062A7C.c`:
  - its func_800527C0 arity is now covered by E20f (`E20f-empty-callees.md`);
  - what remains is `guest-address result of func_8005DC4C bound to host pointer str`.
- The live definition was the hand shortcut `func_8005F594(func_8005DC4C(id))`.
  It had the same guest effects as the matched body: it runs through the hand
  func_8005F354, which does push, measure, move by
  `(D_8009D138 - w - 4) >> 1`, draw inside push/pop, then pop. The only
  difference is when D_8009D138 is read (before the measure loop instead of
  after it), and the loop never writes D_8009D138, so it can't be observed.
  So no player-visible divergence. The shortcut is retired anyway, in favour
  of the line-by-line port.
- Callers:
  - func_80044E14, the item-label window at +0x30;
  - func_8004DA04 (MemCard_DrawProgress, message D_8009D000);
  - func_80047714 (Menu_DrawEquipScreenHeader, message 0x69);
  - func_8004D690 (window record +0x24 - 0x11).

## Consumers

0x80044E14 is only ever stored into window+0x30. There are two `jalr` sites
through +0x30:

    800628dc  lw    v0,48(s0)
    800628e4  jalr  v0                ; menu window tick: next ops overwrite v0
    800628ec  lw    v1,956(gp)
    800628f0  lui   v0,0x800a         ; $v0 dead

    800d46e0  jalr  v0                ; func_800D4698 CTX dispatcher
    800d46e8  sw    v0,20(s0)         ; $v0 stored to ctx+0x14: READ

Because 0x800D46E0 reads the result, func_80044E14 must return the real
value.

## Port

- `pc_port/game/decomp_hand/func_80044E14_port.c`:
  - `PE_V0_func_80062A7C`, a line-by-line port of src/func_80062A7C.c on
    guest addresses, with the draw-state stack push/pop, plus the retail `$v0`.
  - `void func_80062A7C(uint32_t)`, the same port with the value discarded.
  - `int func_80044E14(pe_addr_t)`, which follows src/func_80044E14.c.
  - The header in `pe_port_compat.h` changes from `void` to `int`.
  - The native dispatcher `func_800638D8` (the 0x800628E4 path) ignores the
    value, as retail does.
  - The regenerated `zz_dispatch.c` entry `pe_gct_512` now returns it, which
    is the 0x800D46E0 path.
- Tests in `pc_port/tests/test_v0_passthrough.h`:
  - VPASS1: checks the stack against a model of the matched C.
    - The grid is the stack pointer (0x800A2260 to 0x800A22B8, covering
      under-base, empty, mid, full and overflow) by string (glyph string,
      empty string, out-of-range id so str == 0).
    - For each case it checks `$v0`, D_8009D12C, D_8009D124/128 and the
      stack words.
    - The centred x is computed from the generated (matched) func_8005F1A0
      measure.
  - VPASS2: one assertion per path:
    - non-empty (`$v0` = pushed x0);
    - underflow (0);
    - overflow (a stale popped word).
  - VPASS3: func_80044E14 returns the port's `$v0`, or 0 when the entry is
    empty. The label draw before the call (func_8005F594 → func_8005F354,
    whose push/pop is balanced) always leaves D_8009D12C >= D_800A2270, so
    func_80062A7C's underflow `$v0 = 0` path can't be reached through
    func_80044E14. It is pinned directly in VPASS1/VPASS2, and VPASS3
    covers the full-stack (stale-pop) case instead.
